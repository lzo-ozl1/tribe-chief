# 부족장 — Development Rules

## 1. 최우선 개발 원칙
이 문서는 부족장 프로젝트의 개발 기준이다.

### 반드시 지킨다
1. OOP 기반으로 설계한다.
2. 계획을 먼저 제시한다.
3. 사용자 승인을 받은 후 실제 작업을 수행한다.
4. 기존 규칙을 임의로 변경하지 않는다.
5. 성능과 유지보수성을 고려하여 최적화된 구조를 선택한다.
6. 기능과 책임을 클래스/모듈 단위로 분리한다.
7. 모든 주요 변경은 GitHub에서 추적 가능해야 한다.

## 2. 계획 → 승인 → 구현
모든 실질적인 개발 작업은 다음 순서를 따른다.

```text
요구사항 확인
→ 현재 구조 확인
→ 문제/영향 범위 분석
→ 구현 계획 제시
→ 사용자 승인
→ 브랜치 생성
→ 구현
→ 테스트
→ Commit
→ Pull Request
→ 리뷰/수정
→ Merge
```

사용자 승인 전에는 코드, 구조, 규칙을 변경하지 않는다.

## 3. 게임 규칙 보호
- `GAME_DESIGN.md`에 확정된 규칙은 기준점으로 취급한다.
- 규칙 변경이 필요하면 변경 이유와 영향 범위를 먼저 설명한다.
- 사용자 승인 없이 게임 밸런스나 규칙을 임의로 수정하지 않는다.
- 미정 사항은 확정된 것처럼 구현하지 않는다.

## 4. OOP 규칙
- 클래스는 하나의 명확한 책임을 가진다.
- 상속은 실제 IS-A 관계가 있을 때만 사용한다.
- 인터페이스는 실제 다형성 또는 결합도 감소에 필요할 때 사용한다.
- 거대한 God Object를 만들지 않는다.
- 전역 상태를 최소화한다.
- 도메인 객체의 상태 변경은 가능한 한 객체 자신의 메서드를 통해 수행한다.
- UI가 도메인 객체의 내부 상태를 직접 조작하지 않는다.

## 5. 코드 작성 규칙
- 의미가 명확한 이름을 사용한다.
- 함수는 한 가지 책임에 집중한다.
- 중복 코드는 공통 책임으로 추출한다.
- 과도한 추상화는 피한다.
- 주석은 코드가 아니라 의사결정의 이유를 설명하는 데 사용한다.
- 임시 코드에는 명확한 TODO를 남긴다.
- 미사용 코드와 죽은 코드는 남기지 않는다.

## 6. 최적화 규칙
최적화를 목적으로 코드 가독성을 희생하지 않는다.

우선순위:
1. 알고리즘/데이터 구조 개선
2. 불필요한 계산 제거
3. 불필요한 상태 변경/렌더링 제거
4. 객체 생성 및 메모리 사용 최적화
5. 네트워크/저장소 접근 최소화

성능 문제가 명확하지 않은 경우 섣부른 마이크로 최적화를 하지 않는다.

## 7. 테스트 규칙
게임 규칙은 가능한 한 자동 테스트로 검증한다.

최소 테스트:
- 자원 획득
- 자원 공개 규칙
- 보유량 15개 제한
- 공격 성공/실패
- 방어 성공/실패
- 방어 자원 비소모
- 가축 유지
- 카드 구매
- 스킬 카드 지급
- 부족장 보너스
- 15점 종료 조건

버그 수정 시 가능하면 해당 버그를 재현하는 회귀 테스트를 추가한다.

## 8. Git 브랜치 규칙
`main`은 안정된 기준 브랜치로 유지한다.

기능은 별도 브랜치에서 개발한다.

예:
```text
feature/resource-model
feature/point-card
feature/attack-defense
feature/tribe-leader
feature/game-engine
feature/ui
feature/ai
```

버그 수정:
```text
fix/attack-defense
fix/card-purchase
```

## 9. Commit 규칙
커밋 메시지는 변경 목적이 명확하도록 작성한다.

권장 형식:
```text
feat: add resource model
fix: correct livestock maintenance
refactor: separate attack resolution
 test: add resource acquisition tests
 docs: update game rules
```

하나의 커밋은 가능한 한 하나의 논리적 변경을 담는다.

## 10. Pull Request 규칙
PR에는 최소한 다음 내용을 포함한다.
- 변경 목적
- 구현 내용
- 영향 범위
- 테스트 결과
- 성능 영향
- 게임 규칙 변경 여부
- 추가 검토가 필요한 사항

큰 기능은 가능한 한 작은 단위의 PR로 나눈다.

## 11. 기존 코드 수정 규칙
기존 코드를 수정하기 전에:
1. 현재 구조를 읽는다.
2. 관련 클래스와 의존성을 확인한다.
3. 수정으로 영향을 받는 테스트를 확인한다.
4. 변경 계획을 사용자에게 제시한다.
5. 승인 후 수정한다.

단순해 보이는 변경이라도 기존 구조를 무시하고 새 구조를 만들지 않는다.

## 12. 파일/폴더 규칙
- 게임 규칙 문서: `docs/GAME_DESIGN.md`
- 데이터 설계: `docs/DATA_DESIGN.md`
- 시스템 구조: `docs/ARCHITECTURE.md`
- 개발 규칙: `docs/DEVELOPMENT_RULES.md`
- 테스트는 구현 언어/프레임워크의 표준 테스트 구조를 따른다.
- 기능별 파일을 명확하게 분리한다.

## 13. 문서 우선 원칙
코드와 문서의 규칙이 충돌하면 사용자에게 확인한다.

게임 규칙 변경은 코드만 수정해서 끝내지 않는다.
관련 문서를 함께 갱신한다.

## 14. AI 개발 보조 규칙
AI는 다음을 지킨다.
- 사용자 승인 없이 구현하지 않는다.
- 기존 코드를 읽지 않고 수정하지 않는다.
- 요구하지 않은 기능을 임의로 추가하지 않는다.
- 게임 규칙을 임의로 해석하여 확정하지 않는다.
- 더 나은 설계가 있다고 판단하면 먼저 제안한다.
- 성능 개선이 필요하면 근거를 설명한다.
- 변경 범위를 최소화한다.
- 작업 후 무엇을 변경했는지 명확히 보고한다.

## 15. 규칙 변경 절차
개발 규칙 자체를 변경해야 하는 경우에도 동일하게 적용한다.

```text
변경 제안
→ 이유/영향 설명
→ 사용자 승인
→ DEVELOPMENT_RULES.md 수정
→ Commit
→ PR
```

## 16. 핵심 원칙 요약
> 계획 없이 구현하지 않는다.
>
> 승인 없이 변경하지 않는다.
>
> 규칙을 임의로 만들지 않는다.
>
> 책임을 클래스와 모듈로 분리한다.
>
> 최적화는 근거를 가지고 한다.
>
> 모든 변경은 GitHub에서 추적 가능하게 한다.
